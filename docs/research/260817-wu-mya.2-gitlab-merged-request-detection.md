# Research: GitLab merged-request detection for /wurk:cleanup

**Date**: 2026-08-17T16:28:00-0600
**Git Commit**: 053f660428c52f2fd8d2522bfdd30592b936ae28
**Branch**: wu-mya.2-gitlab-cleanup-detection
**Bead**: wu-mya.2

## Research Question

Does the kit's merged-request detection path work against a GitLab remote, and
exactly where does it break or need a forge adapter? Four sub-questions from
the bead: state filter semantics, JSON field names, rebase-merge behavior, and
whether the `Refs:` trailer to bead-close path survives a rebase before merge.

## How this was verified

`glab 1.112.0` is installed and authenticated against gitlab.com as
`johnnyt1`. Every claim marked **verified** below came out of a read-only
`glab` or `glab api` call against a real public project on gitlab.com, run
during this research. Nothing was created, modified, merged, closed, or
pushed. Claims that could not be produced by a read-only call are marked
**derived** and say what they are derived from.

The projects used, and why:

| project | id | `merge_method` | `squash_option` | why |
| --- | --- | --- | --- | --- |
| `gitlab-org/cli` | 34675721 | `merge` | `default_on` | squash-on-merge case |
| `wireshark/wireshark` | 7898047 | `ff` | `default_off` | fast-forward-only (rebase) case |
| `inkscape/inkscape` | 3472737 | `ff` | `default_off` | second fast-forward data point |
| `freedesktop-sdk/freedesktop-sdk` | 4339844 | `rebase_merge` | `default_off` | semi-linear history case |

All four `merge_method` / `squash_option` values above are **verified** from
`glab api projects/<id>`.

## Summary

The detection path is **structurally sound** on GitLab and **breaks in exactly
three mechanical places**, all inside `PrState`. The design decision the path
rests on - "ask the forge, never git ancestry" - holds *more* strongly on
GitLab than on GitHub, and is now backed by live counts rather than inference.

What survives unchanged:

- The kit's normalized `request` shape (`number`, `state`, `head_oid`,
  `merged_at`) maps cleanly onto GitLab fields. No new keys are needed.
- `Forge::REQUEST_MERGED = "merged"` ([`skills/wurk:kit/scripts/lib/forge.rb:33`](https://github.com/riddler/wurk/blob/053f660428c52f2fd8d2522bfdd30592b936ae28/skills/wurk:kit/scripts/lib/forge.rb#L33))
  happens to be GitLab's own spelling of `state`, so the adapter's state
  mapping is the identity function. GitHub is the forge that needs a mapping.
- `Refs.beads_from_messages` ([`skills/wurk:kit/scripts/lib/refs.rb:41-56`](https://github.com/riddler/wurk/blob/053f660428c52f2fd8d2522bfdd30592b936ae28/skills/wurk:kit/scripts/lib/refs.rb#L41-L56))
  needs no change at all. Commit message bodies survive a rebase byte for
  byte, which was verified against a real rebased-then-merged commit.
- Everything above `PrState` - `worktree_survey.rb`, `worktree_cleanup.rb`,
  `skills/wurk:cleanup/SKILL.md` - is already forge-neutral after the mya.1
  work and needs no GitLab-specific edit.

What breaks, all three inside `skills/wurk:kit/scripts/pr_state.rb`:

1. **The list query** (`pr_state.rb:39-43`). `--state merged` does not exist
   on `glab mr list`; the flag is `-M/--merged`, and the default state is
   `opened`, not "all". `--json <fields>` does not exist either; `glab mr list
   -F json` emits the whole object and `--jq` filters it.
2. **The field names** (`pr_state.rb:53-56`). `number` -> `iid`, `mergedAt` ->
   `merged_at`, `headRefOid` -> `sha`. `sha` is on the `mr list` payload;
   `diff_refs.head_sha` is **not** (it appears only on `mr view`), which
   corrects a parenthetical in the mya.1 research.
3. **The commits query** (`pr_state.rb:66-69`). `glab mr view -F json` has no
   `commits` key, and there is no `glab mr commits` subcommand. The only route
   is `glab api projects/:id/merge_requests/<iid>/commits`, and `glab api` has
   **no `--jq` flag** at all, so the filtering has to move into Ruby.

Two traps that are not in the mya.1 research and that a naive adapter would
walk into:

- **Fork MRs match on branch name alone.** `--source-branch` filters on the
  string only, with no regard for `source_project_id`. A fork whose branch is
  named the same as a local branch is a false positive.
- **`-F json` still writes JSON to stdout on failure**, as
  `{"error":{"message":"404 Not Found"}}` (an object, not an array), with exit
  1. `Sh.run(...).success?` already gates this in the kit, so the existing
  structure is safe, but a `--jq`-based adapter that trusted stdout shape
  would not be.

## Detailed Findings

### 1. State filter semantics

**The flag surface, verified** (`glab mr list --help`, glab 1.112.0). There is
no `--state`. Status is three separate boolean flags:

| flag | meaning |
| --- | --- |
| (none) | default: **opened only** |
| `-M`, `--merged` | merged only |
| `-c`, `--closed` | closed only |
| `-A`, `--all` | every state |

Verified directly: `glab mr list -R gitlab-org/cli --source-branch=df-mr-01-migrate-new-model`
(no `-M`) returned `count=0` for a branch whose MR is merged; adding `-M`
returned it; `-A` returned it with `state: "merged"`.

**`--source-branch` matches exactly, not fuzzily.** Verified against
`gitlab-org/cli` MR !3720, source branch `df-mr-01-migrate-new-model`:

| query | result |
| --- | --- |
| `--source-branch=df-mr-01-migrate-new-model` | 1 match |
| `--source-branch=df-mr-01` (prefix) | 0 |
| `--source-branch=migrate-new-model` (substring) | 0 |
| `--source-branch='df-mr-01*'` (glob) | 0 |

This is the behavior the kit wants. It is stricter than `gh pr list --head`,
which is also exact but on GitHub can be given `owner:branch`.

**A merged MR whose source branch was deleted is still returned.** This is
the case cleanup actually runs in, and it is the single most important thing
to confirm. Verified: `gitlab-org/cli` has `remove_source_branch_after_merge:
true`, and `glab api projects/34675721/repository/branches/df-mr-01-migrate-new-model`
returns `404 Branch Not Found`, yet `glab mr list -M --source-branch=df-mr-01-migrate-new-model`
still returns MR !3720. The MR record carries the branch name as a string
independent of whether the ref still exists. No trap here.

**Fork MRs are matched by branch name alone.** Verified: `gitlab-org/cli` MR
!3708 has `source_project_id: 85318062` against `target_project_id: 34675721`,
and `glab mr list -R gitlab-org/cli -M --source-branch=fix/config-yaml-anchor`
returns it. Nothing in the filter distinguishes a fork's branch from a branch
in the project itself. Relatedly, verified: for fork-sourced MRs,
`projects/<target>/repository/branches/<source_branch>` 404s even while the MR
is open, because the branch lives in the fork.

**A source branch can carry many MRs, and the list is ordered by `created_at`
desc by default.** Verified: `renovate/github.com-docker-cli-29.x` in
`gitlab-org/cli` has 23 merged MRs plus one open and three closed. The kit's
`--jq '.[0]'` therefore picks the most recently *created* merged MR for that
branch, not necessarily the most recently *merged* one. `glab mr list` does
offer `-o/--order merged_at -S/--sort desc`; verified that it is accepted and
runs, though on this sample it produced the same ordering as the default.

**Empty and error results, verified:**

| situation | stdout | exit |
| --- | --- | --- |
| `-F json`, no match | `[]` | 0 |
| `-F json --jq '.[0]'`, no match | `null` | 0 |
| text output, no match | `No merged merge requests match your search in <repo>.` | 0 |
| `-F json`, repo 404 | `{"error":{"message":"404 Not Found"}}` | 1 |

The `null` on empty is convenient: it is byte-identical to what
`gh pr list ... --jq '.[0]'` emits, so `pr_state.rb:48`'s
`text.empty? || text == "null"` check needs no change.

**`--jq` requires `-F json`.** Verified: `glab mr list ... --jq '.[0].iid'`
without `-F json` errors with `Using --jq requires --output=json (got
"text")`. There is no allow-list flag; `--jq` is the only filter.

**Repo resolution works the same way.** Verified from a directory whose only
git remote is `https://gitlab.com/gitlab-org/cli.git`: `glab mr list -M -F
json` resolves the project from the remote with no `-R`, and `glab api
"projects/:id"` expands `:id` to the URL-encoded full path and returns
`id: 34675721`, `path_with_namespace: gitlab-org/cli`. `glab api` does **not**
accept `-R/--repo`; placeholders come from the current directory's remote (or
`--hostname`). That is compatible with how kit scripts run, which is always
inside the repo.

**The kit-shaped query, end to end, verified working:**

```
glab mr list -M --source-branch <branch> -F json \
  --jq '.[0] | {iid, merged_at, sha, state, source_branch}'
```

returned

```json
{"iid":3720,"merged_at":"2026-08-17T14:16:10.149Z",
 "sha":"4f971f47a31c588c56a11e34369fc861f848ca9a",
 "source_branch":"df-mr-01-migrate-new-model","state":"merged"}
```

### 2. JSON field names, as actually emitted

**`glab mr list -F json` emits the raw REST MR object.** Verified full key set
(48 keys) for a merged MR:

```
allow_collaboration allow_maintainer_to_push assignee assignees author
blocking_discussions_resolved closed_at closed_by created_at description
detailed_merge_status discussion_locked downvotes draft
force_remove_source_branch has_conflicts id iid imported imported_from
label_details labels merge_after merge_commit_sha merge_user
merge_when_pipeline_succeeds merged_at merged_by milestone prepared_at
project_id references reviewers sha should_remove_source_branch source_branch
source_project_id squash squash_commit_sha squash_on_merge state target_branch
target_project_id task_completion_status time_stats title updated_at upvotes
user_notes_count web_url
```

The mapping the kit needs:

| kit key (`pr_state.rb`) | gh field | GitLab field | note |
| --- | --- | --- | --- |
| `number` | `number` | `iid` | `id` is the global id; `iid` is the per-project number in the UI and in `glab mr view <n>` |
| `merged_at` | `mergedAt` | `merged_at` | ISO 8601 **with milliseconds**: `2026-08-17T14:16:10.149Z`. gh emits second precision. |
| `head_oid` | `headRefOid` | `sha` | see below |
| (state) | `state` + non-null `mergedAt` | `state == "merged"` | single field is sufficient |

**Correction to the mya.1 research.** That document says `headRefOid` ->
"`sha` (or `diff_refs.head_sha`)". Verified: `glab mr list -F json` does
**not** emit `diff_refs` (`.[0] | has("diff_refs")` returns `false`), while
`glab mr view -F json` does. For `wireshark/wireshark` !26206 the two agree:
`sha` and `diff_refs.head_sha` are both
`45cc01084d0b3e7b727fbfc39e7599876cc1af2d`. So `sha` is the field to use on
the list path, and `diff_refs.head_sha` is not an available alternative there.

**`glab mr view -F json` emits a superset** (67 keys), adding `changes_count`,
`diff_refs`, `diverged_commits_count`, `first_contribution`, `head_pipeline`,
`merge_error`, `pipeline`, `rebase_in_progress`, `subscribed`, `user`,
`work_in_progress`, and others. Verified: it does **not** include a `commits`
key. There is no `commits` anywhere in the MR payload.

**`sha` tracks the source branch tip exactly.** Verified on four open
same-project MRs in `gitlab-org/cli` (!3734, !3733, !3732, !3730): in every
case `mr.sha` equals `projects/34675721/repository/branches/<source_branch>`'s
`commit.id`. This matters for section 3.

**The commits path has no `glab mr` equivalent.** Verified from `glab mr
--help`: the subcommands are `approve approvers checkout close create delete
diff for issues list merge note rebase reopen revoke subscribe todo
unsubscribe update view`. No `commits`. The only route is:

```
glab api "projects/:id/merge_requests/<iid>/commits"
```

Verified return shape, per commit:

```
id short_id created_at parent_ids title message author_name author_email
authored_date committer_name committer_email committed_date trailers
extended_trailers web_url
```

Two notes on that:

- `message` is the **full** commit message (subject plus body), not just the
  body. `gh pr view --json commits --jq '.commits[].messageBody'` returns the
  body only. `Refs.beads_from_messages` anchors on `/^Refs:/` per line
  (`refs.rb:42`), so including the subject line is harmless: a subject can
  never match `^Refs:` in practice, and if it did it would be a genuine
  trailer anyway. No behavior change.
- GitLab parses git trailers server-side and exposes them as `trailers` and
  `extended_trailers` maps. Verified present on every commit object, empty
  (`{}`) for commits without trailers. The kit does **not** need this - and
  arguably should not use it, since `refs.rb` is the kit's single definition
  site for trailer extraction and it is manifest-keyed - but it exists, and
  a reader of the raw payload will see it.
- **`glab api` has no `--jq` flag.** Verified from its full flag list
  (`--field --form --header --help --hostname --include --input --method
  --output --paginate --raw-field --silent`). The only `jq` mentions in its
  help are about piping `--output ndjson` to an external `jq`. So unlike the
  gh path, the commits filtering cannot be pushed into the CLI; the adapter
  has to `JSON.parse` in Ruby and map `.map { |c| c["message"] }`. This is
  compatible with ADR-0006 (stdlib only) since `json` is stdlib.
- `glab api` supports `--paginate`. The commits endpoint is paginated at 20
  per page by default, so a branch with more than 20 commits needs it.
  (Pagination limits are **derived** from the GitLab REST API defaults; the
  MRs sampled here had 1 and 2 commits, so the page boundary was not
  exercised live.)

### 3. Rebase-merge behavior, and why ancestry stays wrong

The kit's rule (`pr_state.rb:12-29`, [`skills/wurk:cleanup/SKILL.md:19-44`](https://github.com/riddler/wurk/blob/053f660428c52f2fd8d2522bfdd30592b936ae28/skills/wurk:cleanup/SKILL.md#L19-L44)) is
that a merged branch's tip is never an ancestor of the target, so ancestry
detection silently no-ops forever. On GitLab this is true *more often* and for
*more merge settings* than on GitHub.

**Method.** For each merged MR, `glab api
projects/<id>/repository/merge_base?refs[]=<mr.sha>&refs[]=<target_branch>`.
If the merge base equals `mr.sha`, the recorded head is an ancestor of the
target; otherwise it is not.

**Verified counts over the 25 most recent merged MRs per project:**

| project | `merge_method` | squash | `sha` is ancestor | `sha` is NOT ancestor |
| --- | --- | --- | --- | --- |
| `gitlab-org/cli` | `merge` | `default_on` | 6 | **19** |
| `wireshark/wireshark` | `ff` | off | 12 | **13** |
| `freedesktop-sdk/freedesktop-sdk` | `rebase_merge` | off | 25 | 0 |

**What each GitLab merge-method setting produces** (the settings-to-outcome
mapping the bead asks for):

| `merge_method` | GitLab UI name | `merge_commit_sha` | `squash_commit_sha` | is `mr.sha` an ancestor of the target? |
| --- | --- | --- | --- | --- |
| `merge` | Merge commit | set (verified) | set when squashed (verified) | **No** when squashed; yes when not squashed and the branch commits land unrewritten |
| `merge` + squash | Merge commit, squash on | set | set | **No**. Verified 19/25 in `gitlab-org/cli`. |
| `ff` | Fast-forward merge | `""` (verified) | `""` | **Sometimes**. Yes if the branch already sat on top of the target (pure fast-forward); no if a rebase replayed it. Verified 13/25 not-ancestor in `wireshark/wireshark`. |
| `rebase_merge` | Merge commit with semi-linear history | set (verified; equals `sha` for single-commit fast-forwardable MRs) | `""` | Yes in the 25 sampled. |

Note that under `ff` a merged MR has `merge_commit_sha: ""` (empty string, not
`null`) - verified on every `wireshark` and `inkscape` merged MR sampled. So
an adapter must **not** treat "has a merge commit" as the merged signal.
`state == "merged"` is the only reliable one.

**The decisive single case, verified end to end.** `wireshark/wireshark`
!26206, source branch `ws_label_strcpy`, target `master`, `merge_method: ff`:

| | sha | parent | authored | committed |
| --- | --- | --- | --- | --- |
| MR head (`mr.sha`) | `45cc01084d0b3e7b727fbfc39e7599876cc1af2d` | `e0127775...` | 2026-08-17T08:13:45-04:00 | 2026-08-17T08:30:43-04:00 |
| landed on `master` | `2a99fbbb...` | `a9e15236...` | 2026-08-17T08:13:45-04:00 | 2026-08-17T09:29:19-04:00 |

Different sha, different parent, same author date, and a **byte-identical
commit message**. `merge_base(45cc0108, master)` is `e0127775`, not
`45cc0108`, so the MR's recorded head is unreachable from `master`. This is
the textbook rebase-merge failure that `pr_state.rb`'s header describes,
observed on a live GitLab project.

**Consequence for `worktree_cleanup.rb:132-139`.** That block compares the
worktree's local `git rev-parse HEAD` against `request["head_oid"]` and skips
with "commits after merge" when they differ. On GitLab there is a case that
does not exist on GitHub: GitLab's server-side rebase (the "Rebase" button,
`glab mr rebase`, or an `ff`/`rebase_merge` merge that rebases first)
**rewrites the source branch ref**, and since `mr.sha` tracks the source
branch tip exactly (verified in section 2), `mr.sha` becomes the rebased sha
while the developer's local branch still holds the pre-rebase sha. The
comparison then reports "commits after merge, skipped" for a worktree that is
in fact clean and fully merged.

This consequence is **derived**, not verified: confirming it would require
rebasing and merging a real MR, which is out of scope for read-only research.
The two facts it is built from are each verified independently (`mr.sha`
equals the source branch tip; a server rebase rewrites that ref). It is
recorded as an open question below rather than as a finding.

### 4. Refs trailer to bead close, under rebase and under squash

**Under rebase: trailers survive, verified.** The !26206 evidence above is the
proof. The rebase produced a new sha with a byte-identical message body. Any
`Refs: wu-xxx` trailer in that body would have survived unchanged.
`Refs.beads_from_messages` keys on `/^Refs:/` per line and on the manifest's
bead-id pattern (`refs.rb:41-56`); neither is sha-sensitive. Nothing in the
bead-close path needs a GitLab-specific change.

**Which command returns the merged MR's commits.** Only
`glab api projects/:id/merge_requests/<iid>/commits`, as established in
section 2.

**Which shas it returns: the MR's recorded source-branch commits, not the
commits as they landed.** Verified on !26206: the endpoint returned exactly
one commit, `45cc0108` - the pre-rebase sha, matching `mr.sha` - and **not**
`2a99fbbb`, the sha on `master`. Verified across every sampled MR in all four
projects: the first entry of the commits list always equals `mr.sha`.

So the endpoint is the MR-side view, frozen at whatever the source branch last
was. That is exactly what the kit wants: it reads *messages*, not shas, and
message bodies are identical on both sides of a rebase. It also means the
endpoint cannot be used to learn the landed shas, which the kit never asks
for.

**Under squash-on-merge: the trailers are lost from the target branch, but
not from the endpoint the kit reads.** Verified on `gitlab-org/cli` !3720
(`squash: true`):

- The commits endpoint returns the 2 original source-branch commits with their
  full messages intact, including the multi-paragraph body.
- The squash commit that landed on `main`
  (`3274a36a9fed53c4e3a02a73dde64a2b2b5b3aa6`, verified to be an ancestor of
  `main`) has the message `"refactor(df): remove npm-config model\n"` - the
  **MR title only**. Both original commit bodies, and therefore any trailers
  in them, are gone from the target branch's history. Its `trailers` map is
  `{}`.

The practical statement: under squash-on-merge, a `Refs:` trailer written in a
commit is **not** recoverable from `git log` on the default branch, but **is**
recoverable from the MR commits endpoint. The kit reads the endpoint
(`pr_state.rb:65-74` -> `worktree_cleanup.rb:153-161`), so `/wurk:cleanup`
keeps working; a hypothetical ancestry-or-git-log implementation would close
nothing. GitLab does offer a project-level squash commit message template that
can include the source commit messages, but the default does not, and the
default is what was observed here.

## Architecture Documentation

The seam this bead probes is the one ADR-0004 predicts: a structural
difference between consumers arrives as a manifest enum
(`forge.kind: github | gitlab`), and the generic skill reads it rather than
forking. `Forge.guard!` is the current expression of that - four call sites
(`pr_state.rb:84`, `worktree_survey.rb:81`, `worktree_cleanup.rb:50`,
`permalinks.rb:85`) that block with `unsupported_forge` rather than
half-working.

ADR-0006's banned-operation list already names `glab mr create` alongside
`gh pr create` (`contract_test.rb:36`), so a read-only GitLab adapter sits
inside the existing contract without amending it. Everything this research
exercised - `glab mr list`, `glab mr view`, `glab api ... GET` - is read-only,
and all of it would go through `lib/sh.rb` per the same contract.

The mya.1 work (commits `0dd5639` through `053f660`) already removed every
GitHub-specific spelling from the kit's own vocabulary: `Forge::REQUEST_MERGED`
replaced the literal `"MERGED"`, `gh_available` became `forge_available`,
`gh_unavailable` became `forge_unavailable`, and the `pr` key became `request`.
The consequence for this bead is that the GitLab adapter's blast radius is one
file. Nothing in `worktree_survey.rb`, `worktree_cleanup.rb`, or
`skills/wurk:cleanup/SKILL.md` names a forge or a GitHub concept any more.

[`docs/plan.md:1183-1186`](https://github.com/riddler/wurk/blob/053f660428c52f2fd8d2522bfdd30592b936ae28/docs/plan.md#L1183-L1186) (phase 4, bead `wu-4wl`) places the GitLab
implementation in `pr_state.rb` and `permalinks.rb` in place, rather than in a
new adapter file. This research does not contradict that: the three breaks are
all in `pr_state.rb`, and they are three argv constructions plus a field
mapping.

## Open Questions

1. **Does a GitLab server-side rebase break `worktree_cleanup.rb:132-139`?**
   The two component facts are verified (`mr.sha` equals the source branch
   tip; a server rebase rewrites that ref), but the composed behavior was not,
   because verifying it requires rebasing and merging a real MR. If it holds,
   a clean, fully merged worktree would be reported as "commits after merge,
   skipped" whenever the operator used GitLab's Rebase button. Needs a
   throwaway project on gitlab.com to settle.

2. **Which of the three GitLab merge settings will the first GitLab consumer
   actually use?** The bead says "merges rebase-only", which maps to either
   `ff` or `rebase_merge`. The two behave differently in the sample: `ff`
   produced 13/25 non-ancestor heads and `merge_commit_sha: ""`, while
   `rebase_merge` produced 25/25 ancestor heads and a populated
   `merge_commit_sha`. Both are safe under a `state == "merged"` check; only
   an ancestry-based check would care. Unanswerable from this repo.

3. **Does the consumer squash on merge?** If so, `Refs:` trailers are absent
   from the default branch's history (verified), and only the MR commits
   endpoint recovers them. That is fine for `/wurk:cleanup` as written, but it
   is a constraint on any future feature that wants to derive beads from
   `git log` on the default branch.

4. **Should the adapter reject fork-sourced MRs?** `--source-branch` matches on
   name alone across projects (verified). Comparing `source_project_id` to
   `target_project_id`, or to the project resolved from the remote, would
   close the false-positive window. Whether the kit should care depends on
   whether the consumer takes fork contributions at all.

5. **Pagination on the commits endpoint.** `glab api --paginate` exists, and
   the GitLab default page size of 20 is documentation-derived, not exercised
   here - the sampled MRs had one and two commits. A branch with more than 20
   commits would need `--paginate` for the bead extraction to be complete.

6. **Ordering when a source branch carries several merged MRs.** Verified that
   this happens in practice (23 merged MRs on one renovate branch) and that
   the default order is `created_at` desc. Whether `.[0]` should instead be
   `-o merged_at -S desc` is a judgment call the adapter has to make
   explicitly rather than inherit.

7. **Self-hosted GitLab.** `glab` resolves the host from the git remote and
   `glab auth`, so the list and commits calls need no host configuration. The
   permalink format does, and `manifest.rb:71` shows the `forge` schema has
   only `kind` and `labels`. Out of scope for this bead but adjacent to it;
   already open question 2 in the mya.1 research.
