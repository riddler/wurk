# Research: gh-only assumptions in wurk:mr and the kit, and their glab equivalents

**Date**: 2026-08-17T14:02:37-0600
**Git Commit**: 5fa3ab89cb68b6a3380983e926f564a595b72608
**Branch**: wu-mya.1-gh-only-audit
**Bead**: wu-mya.1

## Research Question

Map, as the code exists today, every place in `skills/` prose and in
`skills/wurk:kit/scripts/` (and its tests) that talks to the forge; where it
branches on `forge.kind` and where it silently assumes `gh`; the specific
shapes the bead names - request creation, request lookup, permalink format,
close-line syntax, and PR-vs-MR wording surfaced to the operator - plus how
the contract test suite is structured so a new contract test could be added.

## Summary

The forge surface is small and already has a seam. `lib/forge.rb` is the one
module that answers "is this forge implemented?", `IMPLEMENTED` is
`%w[github]`, and four scripts call `Forge.guard!` before touching anything
forge-shaped. Under `forge.kind: gitlab` those four scripts block with
`unsupported_forge` and never shell out - verified behavior, with a dedicated
test each and a `forge_gitlab.json` fixture already in the suite. So the kit
does not half-work on GitLab today; it refuses.

That means the audit's real subject is not "what breaks under gitlab now" but
"what is shaped so that implementing gitlab would silently emit a gh-ism".
Three findings dominate:

1. **Only three `gh` shell-outs exist** (`pr_state.rb` x2, `permalinks.rb`
   x1). Every other script reaches the forge through those. The surface to
   port is genuinely tiny.
2. **The data model downstream of those calls is GitHub-shaped in ways the
   guard does not cover.** The synthesized PR hash uses GitHub's uppercase
   `state: "MERGED"`, the envelope codes are literally named `gh_unavailable`
   / `gh_repo_view_failed`, the survey publishes a boolean field called
   `data.gh_available`, and `permalinks.rb` models repo identity as
   `owner` + `repo` - exactly two path segments, which GitLab subgroups break.
   These are the places a gitlab implementation could pass its own tests and
   still emit a gh-ism.
3. **The operator-facing wording is mostly already neutral, with specific
   exceptions.** `wurk:mr` deliberately says "the request" throughout and
   names the CLI only at the create step. `wurk:cleanup` is the opposite: its
   result strings and report template hardcode "PR #N", "no PR, kept", and it
   surfaces the `gh_unavailable` code to the operator by name. `wurk:mr:268`
   hardcodes `bd note <id> "PR: <url>"`.

On the bead's five named shapes, verified against `glab 1.112.0` installed
locally plus official docs: request creation and permalink format carry real
incompatibilities; request lookup carries two (no field allow-list, and
commits are not in the MR payload); close-line syntax and the draft flag turn
out to be near-non-issues in the code as it stands, because the prose never
states either one.

## Detailed Findings

### The forge seam as it exists

`skills/wurk:kit/scripts/lib/forge.rb` is the single definition site. It
holds three things:

- `IMPLEMENTED = %w[github].freeze` ([`skills/wurk:kit/scripts/lib/forge.rb:18`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/lib/forge.rb#L18))
  - the list whose growth is the phase-4 work.
- `Forge.guard!(env, manifest, doing:)`
  ([`skills/wurk:kit/scripts/lib/forge.rb:29-39`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/lib/forge.rb#L29-L39)) - reads `manifest.forge_kind`,
  and on an unimplemented kind records `code: "unsupported_forge"`,
  `needs: "human"`, naming the manifest path and the operation, then returns
  false so the caller stops and emits.
- `Forge.blob_url(...)` ([`skills/wurk:kit/scripts/lib/forge.rb:44-49`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/lib/forge.rb#L44-L49)) - the
  permalink shape, which `raise`s `ArgumentError` for any kind but `github`
  rather than guessing a URL.

The header comment ([`skills/wurk:kit/scripts/lib/forge.rb:8-14`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/lib/forge.rb#L8-L14)) states the
stance directly: the enum accepts `gitlab` because the schema is shared with a
repo that lives there, nothing implements it, and a `gh` call against a GitLab
repo "fails with a message about authentication, which sends the reader
somewhere useless".

**GitHub's state vocabulary, synthesized rather than passed through**:
[`skills/wurk:kit/scripts/worktree_survey.rb:152`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/worktree_survey.rb#L152) builds
`pr = { number:, state: "MERGED", head_oid:, merged_at: }` - the uppercase
`"MERGED"` is GitHub's PR-state casing, and it is compared literally at
[`skills/wurk:kit/scripts/worktree_cleanup.rb:123`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/worktree_cleanup.rb#L123)
(`pr["state"] == "MERGED"`). This is the sharpest silent-gh-ism candidate in
the kit: GitLab's MR `state` enum is lowercase (`opened`, `closed`, `merged`,
`locked`), so an implementation that passed the forge's own state string
through would compare unequal and every merged worktree would be reported
"not merged ... kept" with no error anywhere.

**Repo identity modeled as exactly two segments**: `permalinks.rb` carries
`owner` and `repo` as separate values from `gh repo view --json owner,name`
through `Permalinks.rewrite` into `Forge.blob_url`
([`skills/wurk:kit/scripts/permalinks.rb:92-123`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/permalinks.rb#L92-L123),
[`skills/wurk:kit/scripts/lib/forge.rb:44-49`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/lib/forge.rb#L44-L49)). GitLab namespaces nest
arbitrarily (`group/subgroup/project`), so the owner/repo pair is not a
faithful model of a GitLab project path.

**"PR" in data keys and result strings**:
`skills/wurk:kit/scripts/worktree_cleanup.rb:124,138,147` produce
`"not merged (no PR, open, or closed unmerged), kept"` and
`"merged in PR #<n>, would remove"`, and
[`skills/wurk:kit/scripts/worktree_cleanup.rb:159`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/worktree_cleanup.rb#L159) produces "could not read
commits for PR #<n>". `pr_state.rb`'s envelope keys are `number`, `merged`,
`head_oid`, `merged_at`; the survey's per-worktree key is `pr`.

### The bead's five named shapes, against glab

Verified against `glab 1.112.0` installed locally (flag surfaces read from
`glab <cmd> --help`) plus official docs.

**1. Request creation.** `glab mr create` differs from `gh pr create` in
every flag the kit would care about:

| Concern | `gh pr create` | `glab mr create` |
|---|---|---|
| Body | `-b/--body`, `-F/--body-file` (`-` = stdin) | `-d/--description`; `-` opens an **editor**, not stdin |
| Body from file | `--body-file <path>` | no equivalent flag; `--template` reads `.gitlab/merge_request_templates/` only |
| Base | `-B/--base` | `-b/--target-branch` (note `-b` means *body* in gh) |
| Head | `-H/--head <branch>` | `-s/--source-branch`; `-H/--head` selects a *repository* |
| Draft | `--draft` | `--draft` (alias `--wip`) |
| Confirm | n/a | `-y/--yes` needed to skip the submission prompt |

The `--description -` / `--body-file -` divergence is the trap: the gh idiom
for delivering a long body is stdin, and the same shape under glab opens an
interactive editor, which in an unattended session hangs rather than errors.
`wurk:mr` states no body-delivery mechanism at all
([`skills/wurk:mr/SKILL.md:242-252`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:mr/SKILL.md#L242-L252) describes body *content*, never how it is
passed), so this is underspecified prose rather than a gh-ism written down -
but it is the step most likely to be improvised gh-shaped.

The **draft flag named in the bead turns out to be absent from the kit
entirely**: no `--draft`, `--web`, `--fill`, `--reviewer`, or `--label` flag
appears on any request-creating command anywhere in `skills/`. There is
nothing gh-shaped to fix; there is simply nothing.

**2. Request lookup.** Three separate incompatibilities:

- **No field allow-list.** `gh pr view --json a,b,c` has no glab analog;
  `glab mr view -F json` emits the whole MR object and you filter with
  `--jq` (which glab does have). Same for `glab mr list -F json`.
- **Field names are the raw REST API's**, not GitHub's GraphQL-flavored ones:
  `number` -> `iid`, `mergedAt` -> `merged_at`, `headRefOid` -> `sha` (or
  `diff_refs.head_sha`), `mergeCommit` -> `merge_commit_sha`.
- **Merged detection is simpler, not harder**: GitLab's `state` enum contains
  `merged` directly, where GitHub needs `state` plus a non-null `mergedAt`.
  The lowercase casing is what collides with
  `worktree_survey.rb:152`'s synthesized `"MERGED"`.
- **Commits are not in the MR payload.** `pr_state.rb beads`
  (`gh pr view <n> --json commits`) has no single-command glab equivalent; it
  needs `glab api projects/:id/merge_requests/:iid/commits`. `glab api`
  exists with `--paginate`.

Listing merged requests for a branch: `gh pr list --state merged --head <b>`
becomes `glab mr list --source-branch <b> --merged`. glab has no unified
`--state <value>`; status is separate boolean flags (`-M/--merged`,
`-c/--closed`, `-A/--all`), default "opened".

**3. Permalink format.** Two differences, both in
`Forge.blob_url` ([`skills/wurk:kit/scripts/lib/forge.rb:44-49`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/lib/forge.rb#L44-L49)):

- The path carries GitLab's scoped-route separator:
  `https://gitlab.com/{namespace}/{project}/-/blob/{sha}/{path}` - the `/-/`
  is mandatory.
- **The line-range anchor differs**: GitHub is `#L10-L20`, GitLab is
  `#L10-20` - the `L` prefixes the start line only. The kit builds
  `"L#{line}-L#{end_line}"` ([`skills/wurk:kit/scripts/lib/forge.rb:47`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/lib/forge.rb#L47)).
  A range anchor copied verbatim to GitLab does not resolve to the range.

Plus the structural point above: `{namespace}` may contain slashes, so
`owner` + `repo` is not sufficient to address a GitLab project. `glab repo
view -F json` returns the project object, whose `path_with_namespace` and
`web_url` are the faithful sources.

**4. Close-line syntax.** GitLab accepts the same keyword families as GitHub
(Close/Closes/Closed/Closing, Fix/Fixes/Fixed/Fixing,
Resolve/Resolves/Resolved/Resolving), and self-managed instances can
customize the pattern. The reference sigils differ: `#123` is an issue,
`!123` is a **merge request, not an issue**, and cross-project is
`group/project#123`.

In the code as it stands this is close to a non-issue.
[`skills/wurk:mr/SKILL.md:255-258`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:mr/SKILL.md#L255-L258) gives **no literal close-line example** on
either forge: under the default `beads` topology the close lines name bead
ids, which are not forge issues at all and trigger no auto-close anywhere;
under `beads-with-forge-projection` the prose defers to "that forge's syntax"
and the topology is unimplemented. The `!` vs `#` distinction becomes
load-bearing only when projection lands. No `Closes #N` / `Fixes #N` string
exists anywhere in `skills/`.

([`skills/wurk:commit/SKILL.md:262`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:commit/SKILL.md#L262)'s "Fixes ..." is s-form commit-subject
style, unrelated to forge auto-close keywords.)

**5. PR-vs-MR wording.** Covered under "Skill prose" above. Summary: `wurk:mr`
neutral except `bd note "PR: <url>"`; `wurk:cleanup` gh-shaped in its result
strings and report examples; `wurk:commit` and `wurk:kit` write "PR/MR"
explicitly; the kit's envelope codes and `data.gh_available` carry the CLI
name into every forge's output.

### The test suite, and where a new contract test would sit

**Discovery** is a glob: [`skills/wurk:kit/scripts/test/run.rb:18-19`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/test/run.rb#L18-L19) requires
every `**/*_test.rb` under `test/`, sorted. No registration step. Minitest
from stdlib, `-n /pattern/` for subsets.

**`contract_test.rb` is a static source scanner**, 648 lines in two halves:

- `module Contract` ([`skills/wurk:kit/scripts/test/contract_test.rb:29-275`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/test/contract_test.rb#L29-L275)) -
  pure functions over lines of source. `each_code_line`
  (`:72-79`) strips trailing `#` comments via `code_only` (`:68-70`) and
  skips blanks, so **comments are exempt from every rule**. Rules are tables
  of label -> regex: `BANNED_CALLS` (`:30-39`, containing `git push`,
  `gh pr create`, `glab mr create`, `bd close`, `bd edit`),
  `CONSUMER_VOCABULARY` (`:153-159`), `HARDCODED_REFS` (`:260-264`),
  `WRITE_CALL` (`:58`). Argv arrays are matched by normalizing quotes,
  brackets and commas to spaces first (`:97-99`) so `["git", "push"]` and
  `"git push"` hit the same phrase regex.
- `class ContractRulesTest` (`:277-418`) unit-tests each pure function
  against synthetic strings, proving the regexes catch and do not over-catch.
- `class ContractTest` (`:423-648`) applies them to the real tree:
  `non_test_files` (`:433-436`) globs `scripts/**/*.rb` minus `scripts/test/`,
  each rule gets one method collecting `"#{file}:#{lineno} (#{label})"` into
  an offenders array closed by `assert_empty`. Markdown rules scan
  `skills/wurk:*/SKILL.md` every line (`:526-538`) and
  `skills/wurk:kit/REFERENCE.md` shell fences only (`:540-547`).
- Two **meta tests** (`:564-582`, `:587-612`) plant a violation in a tmpdir
  and assert the scan catches it, so no rule can go vacuously green.
- A **drift check** (`:629-647`) re-reads
  `docs/adr/0006-ruby-stdlib-scripts-with-envelope-contract.md`, extracts the
  backticked operations from its "banned-operation list is absolute"
  paragraph, subtracts `NON_OPERATIONS` (`:625-627`), and asserts each is
  covered by `BANNED_CALLS` or a fixture's guarded paths. ADR text and test
  coverage cannot part silently.

**`HARDCODED_REFS` is the closest structural precedent for a forge-ism rule**
([`skills/wurk:kit/scripts/test/contract_test.rb:255-274`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/skills/wurk:kit/scripts/test/contract_test.rb#L255-L274)): it bans
*ref-shaped spellings* of a default branch, and its comment records the
tightening that made it usable - bare `main` is also git-worktree vocabulary,
so the rule matches only `origin/main`, `main...HEAD`, `refs/heads/main`.
A gh-ism rule would face the same shape of problem in reverse: `gh` cannot be
banned outright, because `github` is an implemented forge and
`pr_state.rb:40` legitimately spells it.

**Behavioral testing at the forge boundary** is the other established idiom,
and it is already forge-aware:

- `test/support/fake_sh.rb` - `FakeSh` installed as `Sh.runner`; `expect`
  matches an argv **prefix**; an unexpected command raises
  `FakeSh::UnexpectedCommand` (`:60`); `@fake.calls` records what was
  attempted.
- `test/support/manifest_helper.rb` - `with_manifest(name)` installs a
  fixture as `Manifest.current`; `manifest_with(name, overrides)` deep-merges
  one field; `in_tmp_repo` builds a scratch repo carrying `.claude/wurk.json`;
  `all_fixture_guarded_paths` unions the fixtures' guarded paths for
  `contract_test.rb`.
- `test/fixtures/manifests/forge_gitlab.json` - **already exists**, with
  `"forge": {"kind": "gitlab"}`, prefix `zz`, `branch-in-place`.
- Four tests already drive it: `pr_state_test.rb:39-46`,
  `permalinks_test.rb:213-226`, `worktree_survey_test.rb:38`,
  `worktree_cleanup_test.rb:42`. Each asserts exit 1,
  `blocked.first["code"] == "unsupported_forge"`, and - the load-bearing
  assertion - `assert_empty @fake.calls`, i.e. no shell-out was attempted.
  Each carries a `# sabotage:` comment naming what dropping the guard would
  do. A fifth, `permalinks_test.rb:26-31`, asserts `Forge.blob_url` raises
  `ArgumentError` for `kind: "gitlab"` at the pure-function level.

The idiom for a new `*_test.rb`: filename ending `_test.rb` anywhere under
`test/`; `require "minitest/autorun"`, `require_relative "../<script>"`,
`require_relative "support/manifest_helper"` and/or `"support/fake_sh"`;
`class FooTest < Minitest::Test`; `include ManifestHelper`; `setup` builds
`@fake = FakeSh.new; Sh.runner = @fake`, `teardown` does
`Sh.runner = nil; Manifest.reset!`; methods named `test_*`.

Notably, **neither `pr_state_test.rb` nor `permalinks_test.rb` scans script
source for GitHub-isms** - enforcement at the forge boundary is entirely
behavioral today, through `FakeSh`. A source-scanning forge rule would be new
in kind; a fixture-driven behavioral one would extend what already exists.

## Open Questions

1. **Does the new GitLab consumer use nested subgroups?** The `owner`/`repo`
   pair in `permalinks.rb` and `Forge.blob_url` is a two-segment model. If the
   consumer's project path is `group/project` the existing shape stretches; if
   it is `group/subgroup/project` the model itself is wrong. Unanswerable from
   this repo - `wu-mya`'s consumer is not named here and its manifest is not
   in this checkout.
2. **Is the consumer on gitlab.com or self-hosted?** `Forge.blob_url`
   hardcodes the host alongside the path shape. A self-hosted instance needs
   the host from somewhere - `glab repo view -F json`'s `web_url`, or a new
   manifest field. Nothing in the current schema carries a forge host.
3. **Should `forge.labels` remain unread?** It is schema-legal, documented
   with an example, has a typed accessor, and has no reader in any script or
   skill. [`docs/plan.md:1184`](https://github.com/riddler/wurk/blob/5fa3ab89cb68b6a3380983e926f564a595b72608/docs/plan.md#L1184) anticipates `--label agent-filed` at the
   `wurk:mr` create step, which would be its first consumer. Whether that is
   in scope for this bead is a scoping call, not a research finding.
4. **What does a "contract test" mean for a forge-ism, given the ban cannot
   be on the string `gh`?** The two available shapes are structurally
   different - a source-scanning `Contract` rule in the
   `HARDCODED_REFS` mould (new in kind for the forge boundary), or a
   fixture-driven behavioral test through `FakeSh` in the mould of the four
   existing `forge_gitlab` guard tests. The bead says "add a contract test
   where a script would silently emit a gh-ism under gitlab", and the
   sharpest such site found is `worktree_survey.rb:152`'s uppercase
   `"MERGED"` compared at `worktree_cleanup.rb:123`. Which mechanism to use
   is a design decision for the plan stage.
5. **Does `worktree_refresh.rb` relaying `survey_failed` instead of guarding
   in its own voice count as in scope?** It is a forge-dependency reporting
   gap of exactly the kind `worktree_cleanup.rb:44-47` was written to avoid,
   but it is a diagnostics question rather than a gh-ism, and the bead's
   scope is gh-shaped assumptions.
