# gh-only audit: forge-neutral kit vocabulary and a contract rule

## Overview

Sweep the kit and the skill prose for GitHub-CLI assumptions that would
survive `Forge.guard!` - the ones that will not error when `gitlab` joins
`Forge::IMPLEMENTED`, but will quietly produce a wrong answer or a
GitHub-shaped string on a GitLab repo. Replace each with a forge-neutral
form, then add a `Contract` rule so the class of mistake cannot come back.

Beads issue: `wu-mya.1`

This is the audit-plus-fixes-plus-contract-test bead, not the GitLab
implementation. `Forge::IMPLEMENTED` stays `%w[github]` at the end of this
plan; `docs/plan.md` phase 4 (bead `wu-4wl`) owns growing it.

## Current State Analysis

The forge seam already exists and already refuses GitLab, verified by the
research document `docs/research/260817-wu-mya.1-gh-only-assumptions-and-glab-equivalents.md`:

- `skills/wurk:kit/scripts/lib/forge.rb:18` holds `IMPLEMENTED = %w[github]`,
  and `Forge.guard!` (`skills/wurk:kit/scripts/lib/forge.rb:29-39`) blocks
  with `unsupported_forge` / `needs: "human"`.
- Four scripts call it: `pr_state.rb:84`, `permalinks.rb:85`,
  `worktree_survey.rb:81`, `worktree_cleanup.rb:50`. Each has a test that
  drives the `forge_gitlab.json` fixture and asserts exit 1 plus
  `assert_empty @fake.calls`.
- `Forge.blob_url` (`skills/wurk:kit/scripts/lib/forge.rb:44-49`) raises
  `ArgumentError` for any kind but `github`, so the permalink shape cannot
  silently guess either.

So nothing half-works on GitLab today. What is missing is protection for the
day the guard opens. Four surfaces sit downstream of the guard and would pass
their own tests while emitting a gh-ism:

1. **A synthesized GitHub state string.** `worktree_survey.rb:152` builds
   `pr = { number:, state: "MERGED", head_oid:, merged_at: }` and
   `worktree_cleanup.rb:123` compares `pr["state"] == "MERGED"` literally.
   GitLab's MR `state` enum is lowercase (`opened`, `closed`, `merged`,
   `locked`). An adapter that passed the forge's own state through would
   compare unequal, and every merged worktree would report "not merged ...
   kept" with no error anywhere. This is the sharpest silent failure in the
   kit.
2. **Envelope codes and a data field named after the CLI.**
   `gh_unavailable` at `pr_state.rb:103`, `pr_state.rb:120`,
   `worktree_survey.rb:158`, `worktree_cleanup.rb:106`;
   `gh_repo_view_failed` / `gh_repo_view_unparseable` at `permalinks.rb:94`
   and `permalinks.rb:102`; `env.data[:gh_available]` at
   `worktree_survey.rb:108`, read at `worktree_cleanup.rb:105`. Codes are the
   machine-readable half of the envelope contract and `wurk:cleanup`'s prose
   routes on one of them by name (`skills/wurk:cleanup/SKILL.md:163`).
3. **Operator-facing "PR" wording produced by generic scripts.**
   `worktree_cleanup.rb:124`, `:147`, `:156`, `:180` emit "no PR", "merged in
   PR #N", "could not read commits for PR #N"; the survey's per-worktree key
   is `pr`. `skills/wurk:cleanup/SKILL.md:79,170-172,187-193` mirrors those
   strings, so prose and script are gh-shaped together.
   `skills/wurk:mr/SKILL.md:268` hardcodes `bd note <id> "PR: <url>"`, which
   is the string that lands on the bead on every forge.
4. **A forge dependency reported in someone else's voice.**
   `worktree_refresh.rb:79` calls `WorktreeSurvey.run` and re-blocks with
   `survey_failed` (`worktree_refresh.rb:83-86`), so under a gitlab manifest
   the operator sees `survey_failed` wrapping the guard rather than
   `unsupported_forge` - exactly the relay `worktree_cleanup.rb:44-47` was
   written to avoid.

The contract suite that would police this is a static source scanner:
`skills/wurk:kit/scripts/test/contract_test.rb` holds `module Contract` (pure
functions over source lines, comments exempt), `ContractRulesTest` (unit
tests proving each regex catches and does not over-catch), `ContractTest`
(applies the rules to the real tree), two planted-violation meta tests, and
an ADR-0006 drift check. `HARDCODED_REFS` (`contract_test.rb:260-264`) is the
closest precedent: a rule that could not ban the bare word `main` and was
tightened to ref-shaped spellings only.

## Desired End State

The kit has its own merge-state vocabulary defined in exactly one place; no
envelope code, data key, or operator-facing string in a generic script names
a forge CLI; every script that depends on the forge blocks in its own voice;
and a `Contract` rule fails the gate if any of those come back.

Verified by: `ruby skills/wurk:kit/scripts/test/run.rb` green, and
`grep -rn 'gh_\|"MERGED"\|PR #' skills/wurk:kit/scripts/*.rb skills/wurk:kit/scripts/lib/*.rb`
returning nothing outside comments.

### Key Discoveries:

- The guard makes a behavioral GitLab test of the synthesis site **vacuous**:
  under `forge_gitlab.json`, `worktree_survey.rb:81` blocks before line 152
  ever runs, so no `FakeSh` fixture can reach the `"MERGED"` synthesis until
  `IMPLEMENTED` grows. Enforcement here has to be structural.
- The rule cannot ban the string `gh`: `pr_state.rb:40,67` and
  `permalinks.rb:92` legitimately spell `gh` in argv, because `github` is an
  implemented forge and those calls sit behind the guard. The same shape of
  problem `HARDCODED_REFS` solved by narrowing to ref-shaped spellings.
- `data.worktrees[].pr` has exactly two readers: `worktree_cleanup.rb:121`
  and the tests. No SKILL.md references it, so renaming the key is contained.
- `Forge::IMPLEMENTED` and `Forge.blob_url`'s `raise` are load-bearing and
  stay exactly as they are (ADR-0004: forge kind is a manifest structural
  enum, not a per-skill fork).
- ADR-0006 bans `gh pr create` and `glab mr create` outright; no phase here
  adds a request-creating code path, and the drift check at
  `contract_test.rb:629-647` keeps that honest.

## What We're NOT Doing

- **Not implementing `gitlab`.** `Forge::IMPLEMENTED` stays `%w[github]`. No
  `glab` shell-out, no GitLab URL shape, no `glab mr list` adapter. That is
  `docs/plan.md` phase 4 / bead `wu-4wl`.
- **Not remodeling repo identity for GitLab namespaces.** `permalinks.rb`
  carries `owner` + `repo` as two segments, which GitLab subgroups
  (`group/subgroup/project`) break, and `Forge.blob_url` hardcodes
  `https://github.com` with no manifest field for a self-hosted host. Both
  are real, but neither is *silent*: `Forge.blob_url` raises for any non-
  github kind. Fixing them means a schema change (a forge host field) and a
  project-path model, which is implementation work, not audit work. File as a
  follow-up bead against phase 4. (Research open questions 1 and 2 land
  here; they ask about a consumer whose manifest is not in this checkout and
  cannot be answered from this repo.)
- **Not renaming `pr_state.rb`.** The script filename is a gh-ism, but
  renaming it touches `REFERENCE.md`, four skills, and every test that
  requires it, for zero behavioral gain. Follow-up bead.
- **Not giving `forge.labels` a reader.** It is schema-legal, documented, and
  unread; `docs/plan.md:1184` anticipates `--label agent-filed` at the
  `wurk:mr` create step as its first consumer. That is phase-4 scope
  (research open question 3). The schema does not change in this plan, so
  `docs/manifest.md` and `lib/manifest.rb` stay in sync by not moving.
- **Not changing the messages inside envelopes to hide the CLI.** Codes go
  neutral because they are the machine-readable contract; messages keep
  naming the command that actually failed ("gh pr list failed: ..."), because
  a diagnostic that will not say which command broke is worse than one that
  names a CLI. This split is stated in phase 2 so a later reader does not
  "finish the job" by scrubbing the messages too.
- **Not touching `skills/wurk:kit/scripts/test/fixtures/plans/real_grammar_snapshot.md`.**
  It is a frozen snapshot of a donor plan used as test input; its "PR-state
  join" wording is data, not kit vocabulary.

## Implementation Approach

Fix the leaks first, cheapest and most dangerous first, then close the door.
Each phase is one coherent rename or behavior change across script + test +
prose, so each commits and gates on its own. The contract rule lands last,
because it is the phase that would be red if any earlier phase were skipped -
which is the point: it encodes phases 1 through 3 as a rule rather than as a
memory.

The rule itself is a `Contract` source scan in the `HARDCODED_REFS` mould,
not a `FakeSh` behavioral test, for the reason in Key Discoveries: the guard
makes the behavioral version unreachable. It bans two narrow shapes - a
quoted GitHub request-state literal, and a `gh_*` / `glab_*` identifier or
envelope code - and deliberately permits `gh` in argv, since that is a real
call to an implemented forge's CLI. Stated as a sentence: *a forge CLI's name
may appear in an argv the guard protects and in a diagnostic message; it may
not appear in the kit's own vocabulary - envelope codes, data keys, or
synthesized values.*

## Phase 4: The contract rule

### Overview

Encode phases 1 through 3 as a `Contract` source rule so the class of leak
cannot return, with the unit tests and the planted-violation meta coverage
the existing rules all carry.

### Changes Required:

#### 1. The rule
**File**: `skills/wurk:kit/scripts/test/contract_test.rb`
**Changes**: a new table beside `HARDCODED_REFS`, with the comment carrying
the narrowing rationale.

```ruby
  # Forge-CLI vocabulary leaking into the kit's own words. A forge CLI's name
  # may appear in an argv the Forge.guard! seam protects (pr_state.rb's
  # ["gh", "pr", "list", ...]) and in a diagnostic message naming what
  # failed; it may not appear in an envelope code, a data key, or a
  # synthesized value, because those are the kit's vocabulary and outlive the
  # forge they were written against.
  #
  # Narrow on purpose, the same tightening HARDCODED_REFS needed: `gh` as a
  # bare word is a legitimate argv element, so the rule keys off the
  # identifier shape `gh_`/`glab_` and off GitHub's quoted request-state
  # enum, neither of which has any innocent spelling in this tree.
  FORGE_VOCABULARY = {
    "forge CLI in kit vocabulary" => /\b(?:gh|glab)_[a-z]\w*/,
    "forge request-state literal" => /"(?:MERGED|OPEN|CLOSED|DRAFT)"/
  }.freeze

  def forge_vocabulary(content)
    hits = []
    each_code_line(content) do |code, lineno|
      FORGE_VOCABULARY.each { |label, re| hits << [lineno, label] if code =~ re }
    end
    hits
  end
```

#### 2. Unit tests, both directions
**File**: `skills/wurk:kit/scripts/test/contract_test.rb` (`ContractRulesTest`)
**Changes**: prove it catches and prove it does not over-catch.

```ruby
  # sabotage: widen the identifier regex to /\bgh\b/ -> the legitimate
  # guarded argv below starts failing
  def test_forge_vocabulary_catches_cli_named_vocabulary
    assert_equal [[1, "forge CLI in kit vocabulary"]],
                 Contract.forge_vocabulary(%(env.block!(code: "gh_unavailable", message: m)\n))
    assert_equal [[1, "forge CLI in kit vocabulary"]],
                 Contract.forge_vocabulary(%(env.data[:gh_available] = true\n))
    assert_equal [[1, "forge request-state literal"]],
                 Contract.forge_vocabulary(%(pr = { state: "MERGED" }\n))
  end

  def test_forge_vocabulary_permits_guarded_argv_and_comments
    assert_empty Contract.forge_vocabulary(%(Sh.run(["gh", "pr", "list", "--state", "merged"])\n))
    assert_empty Contract.forge_vocabulary(%(IMPLEMENTED = %w[github].freeze\n))
    assert_empty Contract.forge_vocabulary(%(REQUEST_MERGED = "merged"\n))
    assert_empty Contract.forge_vocabulary(%(# the gh_unavailable code was renamed in wu-mya.1\n))
  end
```
