# Cleanup: patch-equivalence instead of sha equality after a server-side rebase

## Overview

`worktree_cleanup.rb` refuses to remove a merged worktree whenever the local
`HEAD` differs from the merged request's recorded head sha. On GitLab a
server-side rebase rewrites the source branch ref, so the inequality also
occurs for work that is fully merged - the worktree is kept forever and its
bead is never even gathered, because the skip returns before `beads_for`.

This plan replaces the single equality gate with a two-step check: the sha
equality stays as the fast exact path, and an inequality is then decided by
patch-id containment against the merge target (`git cherry`) rather than
being treated as proof of unmerged work. A worktree is removed only when git
itself says every commit it carries has an equivalent already on the default
branch; anything else keeps the refusal.

Beads issue: `wu-mya.9`

## Current State Analysis

**The comparison.** `skills/wurk:kit/scripts/worktree_cleanup.rb:133-140`:

```ruby
head_res = Sh.run(%w[git rev-parse HEAD], chdir: path, envelope: env)
local_head = head_res.out.to_s.strip
if head_res.success? && local_head != request["head_oid"]
  return [
    { path: path, branch: branch, result: "commits after merge (#{local_head} != #{request['head_oid']}), skipped" },
    []
  ]
end
```

It runs after the merged-state check (`:124`) and the dirty check (`:128`),
and before `beads_for` (`:142`), which is why a false skip also leaves the
bead open.

**Why the inequality is no longer evidence.** `request["head_oid"]` is
`mr.sha`, which tracks the source branch tip exactly
(`docs/research/260817-wu-mya.2-gitlab-merged-request-detection.md` section
2). GitLab's server-side rebase - the Rebase button, `glab mr rebase`, or an
`ff`/`rebase_merge` merge that rebases first - rewrites that ref, so a clean
and fully merged worktree still holding the pre-rebase sha compares unequal.
Reproduced live on gitlab.com under wu-mya.6 (2026-09-12): the MR's sha moved
from `f1703cd4` to `8fb61078` while the MR was still `state: "opened"`, and
the sweep then reported, verbatim, `"commits after merge
(f1703cd4b71f2056d34c430ac7ddfaab76fd854b !=
8fb6107884432a8f55ad92ad08a47c533ffa1ece), skipped"` with
`data.beads_to_close == []`.

**This is not GitLab-only.** Any history rewrite between the local tip and the
merged head produces the same inequality: a re-push that amends, `/wurk:refresh`
rebasing a live worktree after the request was opened, an operator restacking
a chain. `skills/wurk:cleanup/SKILL.md:205-220` already documents that second
cause and already tells the operator to settle it by hand with exactly the
probe this plan automates:

```bash
git -C <worktree> status --porcelain        # must be empty
git cherry <default-branch> HEAD            # every line must start with "-"
```

So the repair is forge-neutral by construction, and the skill's own written
judgment is the specification for it.

**The adapter is correct and out of scope.** `worktree_survey.rb:148-163`
reports `state: "merged"`, `head_oid` = `mr.sha`, `stale: true`;
`request_state.rb:127-156` is the GitLab adapter that produced them. The bead
says so explicitly, and the wu-mya.6 run confirmed it against gitlab.com.

**Constraints the change sits inside.**

- ADR-0006: system Ruby 2.6 floor, stdlib only, one JSON envelope, `--dry-run`
  on every mutating script, every shell-out through `lib/sh.rb`, and the
  banned-operation list (no `git push`, no request creation, no `bd close`, no
  `bd edit`). Nothing here needs any of those relaxed.
- `request_state.rb:12-44` and `skills/wurk:cleanup/SKILL.md:17-37`: git
  ancestry must never be the *merge* signal. This plan does not touch merge
  detection - the forge's `state == Forge::REQUEST_MERGED` remains the only
  thing that can say "merged". Git is consulted only to decide whether to
  *refuse* a removal the forge has already authorized, which is the opposite
  direction of risk and is what `skills/wurk:cleanup/SKILL.md:205-220` already
  sanctions by hand.
- `Contract::HARDCODED_REFS` (`test/contract_test.rb:283-287`) forbids a
  literal `origin/main` in kit source, so the merge target must come from
  `Manifest#remote_default_branch` (`lib/manifest.rb:247-249`).
- `worktree_cleanup_test.rb:204-210` asserts the string `force` appears in
  `worktree_cleanup.rb` exactly once, on a comment line. New code and new
  comments must avoid that word - write "rewritten" or "re-pushed", never
  "force-pushed".

**The freshness problem, which is what makes this a real risk rather than a
one-line change.** `git cherry` can only see commits that are in the local
object store and reachable from `origin/<default>`. The sweep's
`git fetch --prune` runs *after* the per-worktree loop
(`worktree_cleanup.rb:80-84`), and under `--dry-run` it is only rendered into
`commands`, never run. So a probe added naively would be evaluated against
whatever refs the checkout last fetched, and a stale checkout would refuse
exactly the case this bead exists to fix - silently, and in the direction that
looks like the old bug.

**How the script is tested.** `skills/wurk:kit/scripts/test/worktree_cleanup_test.rb`
drives the whole script through `WorktreeCleanup.run` with `FakeSh`
(`test/support/fake_sh.rb`) installed as `Sh.runner`, and the `worktree`
manifest fixture (`test/fixtures/manifests/worktree.json`, prefix `zz`, no
`repo.default_branch`, so `remote_default_branch` is `origin/main`). `FakeSh`
matches an expectation by argv *prefix*, first match wins, FIFO among equal
prefixes - so registration order matters only between expectations that share
a prefix, and `@fake.calls` preserves real call order for ordering assertions.
An argv with no registered expectation raises `UnexpectedCommand`, which is
what makes "no removal expectations registered" a real assertion that nothing
was removed.

## Desired End State

`worktree_cleanup.rb` removes a clean, merged worktree whose local tip differs
from the merged request's head *only because the history was rewritten*, and
keeps refusing one that carries a change the merged request never saw.

Verifiable by:

- `ruby skills/wurk:kit/scripts/test/run.rb` green, including two new tests
  that pin both halves: the wu-mya.6 rebase shape is removed and its bead
  gathered into `beads_to_close`, and a worktree with an unmatched commit is
  skipped with no removal, no branch delete, and an empty `beads_to_close`.
- A third test pinning the unverifiable case: when the probe itself fails, the
  refusal stands and a warning names it.
- `data.results[].result` distinguishes the three outcomes in words an
  operator can act on, and `skills/wurk:cleanup/SKILL.md`'s result vocabulary
  matches the strings the script emits.

### Key Discoveries:

- `worktree_cleanup.rb:133-140` is the whole defect; the returns at `:135` and

- `skills/wurk:cleanup/SKILL.md:205-220` already prescribes

- `worktree_survey.rb:137-141` already runs `git merge-base --is-ancestor` with

- `request_state.rb:12-44` bans git ancestry as a merge signal; this plan must

- `test/contract_test.rb:283-287` (`HARDCODED_REFS`) and

- ADR-0006's `--dry-run` rule is the one contract this change has to reason

  correct (see Phase 1).

## What We're NOT Doing

- **Not touching merge detection.** `request_state.rb`, its GitLab adapter,
  and `Forge::REQUEST_MERGED` are unchanged. Git never gains a vote on whether
  something merged.
- **Not renaming `head_oid`** or any other survey/request field. The bead says
  this is not a field rename, and nothing downstream needs one.
- **Not relaxing on inequality alone.** An inequality the probe cannot resolve
  keeps the refusal. A relaxation that deleted on any inequality would throw
  work away, which is strictly worse than the current false skip.
- **Not adding a forge capability** for "which shas did this request ever
  have" (GitLab's MR `versions` endpoint). Rejected in Implementation
  Approach; the reasons are recorded there so this is not re-argued.
- **Not making the behavior conditional on `forge.kind`.** The failure is a
  history-rewrite failure, not a GitLab failure, and a generic script that
  branches on the forge for something git can answer would be an adapter with
  no adapter seam.
- **Not annotating the wu-mya.2 research document.** The refusal string
  `"commits after merge (<sha> != <sha>), skipped"` is kept verbatim, so
  nothing a reader would grep for in that document is renamed or removed, and
  its `**Later (2026-09-12):**` note already points at wu-mya.9 as the repair.
  (CLAUDE.md's annotate-what-a-reader-greps-for rule.)
- **Not reworking `/wurk:refresh`,** even though it is one producer of the
  benign inequality. It is correct as it stands; only cleanup's reading of the
  result was wrong.

### Recorded open questions

Both were decided inside this plan so it is actionable as written. They are
recorded because they are the two places an operator may want to overrule the
decision, and neither could be put to a human while this plan was written.

1. **Should `--dry-run` run `git fetch --prune`?** Decided: yes, once per
   sweep, before the check loop (Phase 1). The reasoning and the rejected
   alternatives are in Phase 1's Overview. The operator-visible consequence is
   that `worktree_cleanup.rb --dry-run` now touches remote-tracking refs. If
   that is judged to cross ADR-0006's `--dry-run` line, the fallback is to
   fetch only on a non-dry run and have the dry run emit a
   `refs_not_fetched` warning next to every probe-based refusal - at the cost
   that `/wurk:cleanup`'s check phase can then under-report candidates on a
   stale checkout, which is the bug this bead is fixing.
2. **Is patch-identical-but-differently-worded good enough to delete on?**
   Decided: yes. `git cherry` matches on patch id, so a local commit whose
   diff is already on the default branch under a different message is treated
   as landed, and its message is lost with the branch (reflog aside). The
   change itself is on the default branch either way, so the loss is bounded
   to wording on a branch whose work merged. Tightening it (also comparing
   subjects) was rejected as a heuristic layered on a heuristic, with its own
   false refusals on amended trailers.

## Implementation Approach

**The signal.** After the exact-sha path fails, ask git whether every commit
the worktree carries has a patch-equivalent on the merge target:
`git cherry <manifest remote default branch> HEAD`, run in the worktree. Empty
output, or every line starting with `-`, means nothing is left; any `+` line
means at least one commit's change is not on the default branch, and the
refusal stands. A non-zero exit means unknown, and unknown also refuses.

This is exactly the probe `skills/wurk:cleanup/SKILL.md:205-220` already tells
an operator to run by hand, which is the strongest argument for it: the
project has already decided, in writing, that all-`-` is what justifies
removing one of these worktrees. The change is that the script stops handing
that judgment to a human who mostly never gets asked, because the skip is
reported as "commits after merge" and reads like unlanded work.

**Why it is not the banned ancestry check.** Two distinctions, both worth
stating in the code comment. First, direction: ancestry was banned as a way to
*establish* a merge, where a false negative means cleanup silently never runs;
here the forge has already established the merge and git can only *refuse*,
where a false negative means a worktree is kept - visible, reported, and
repairable by hand. Second, power: `git cherry` is patch-id based, so it
answers correctly in precisely the case plain ancestry gets wrong - a rebase
replayed the commits under new shas. Plain ancestry (`merge-base --is-ancestor
HEAD origin/<default>`) is subsumed: when it would say yes, `origin/<default>..HEAD`
is empty and `git cherry` prints nothing at all.

**Alternatives considered and rejected.**

1. **Ancestry against the merge target as the signal.** Rejected as
   insufficient, not as unsafe. It is sound one way (an ancestor tip carries
   nothing extra) but it is false for every rebase-merged branch - which is
   the entire population this script operates on, per
   `request_state.rb:16-30`. It would leave the wu-mya.6 case refused, so it
   fixes nothing. No separate code is needed for it; `git cherry` already
   covers it.
2. **Ask the forge which shas the request ever had.** GitLab's
   `/merge_requests/:iid/versions` records a `head_commit_sha` per diff
   version, so the pre-rebase sha would be found there and the answer would be
   exact, with no patch-id heuristic and no fetch-freshness dependency.
   Rejected for three reasons. (a) No comparable GitHub path: it would need
   force-push timeline archaeology through GraphQL, and `lib/forge.rb:8-17`
   is explicit that a capability implemented for one forge and half-working on
   the other is worse than one that stops with a named block - so this is a
   two-adapter change, plus a network call per diverged worktree, plus a new
   unavailable-degradation path in the script that must not fall back to
   anything. (b) It is narrower where it matters: it answers "was this exact
   sha ever the branch head on the forge", which refuses a local rebase done
   after the push (`/wurk:refresh`, an operator restack) even though every
   patch landed - and `skills/wurk:cleanup/SKILL.md:205-220` says that case is
   safe to remove. (c) It leaves the identical GitHub-side failure unfixed
   until the second adapter lands.
3. **Compare the local commits against the request's own commit list.**
   `request_state.rb:217-238` already fetches those commits, and their
   messages survive a rebase byte for byte (research section 4). But the
   endpoint returns the *pre-rebase* MR-side view (verified, section 4), so in
   the wu-mya.6 shape it returns exactly the shas the local branch already
   has - it would confirm equality with the thing that is already known and
   say nothing about whether the work landed. Matching on message text rather
   than sha would then be a text heuristic that passes for any two commits
   with the same subject.
4. **Drop the check and rely on git's own refusals.** Not available:
   `git worktree remove` refuses only on a dirty tree, and the branch delete
   is `-D` by necessity (`worktree_cleanup.rb:175-178`) because rebase-merged
   branches are never `-d`-deletable. The check is what makes `-D` safe.

**Known failure modes of the chosen signal**, all of which resolve to a
refusal except the last:

- *Squash-on-merge with more than one commit on the branch.* The squashed
  commit's patch is the union of the branch's patches, so no individual local
  commit matches and every line is `+`. The refusal stands - identical to
  today's behavior, since the shas differ in that case too. The no-rebase
  squash case is unaffected: the shas are equal and the fast path never
  reaches the probe.
- *A rebase that resolved conflicts.* The replayed diff differs, so the local
  commit is genuinely not what landed, and `+` is the right answer.
- *An empty local commit.* Reported unmatched; refusal stands.
- *`origin/<default>` stale or the probe failing (no network, missing ref).*
  Refusal stands, with a warning naming why. Phase 1 removes the most common
  cause.
- *Cost.* `git cherry` computes patch ids for `origin/<default>..HEAD` and for
  the target's commits since the merge base. It runs only on a worktree whose
  shas already disagree, on feature-branch-sized history.
- *The one false-removal shape*: a local commit patch-identical to an upstream
  commit but differently worded is treated as landed. Accepted, with reasoning,
  in "Recorded open questions" above.

**Shape of the change.** Two commits of code, then two of prose: fetch ordering
first (so the probe is asked a fair question), the probe and its wiring second
(the behavior change, with both acceptance-criteria tests), the ADR third, and
`/wurk:cleanup`'s own prose last. The ADR comes before the skill edit because
the skill cites it by number - written the other way round, the skill would
point at a record that does not exist yet for the length of one commit.

## Phase 1: Fetch before the check phase, not after it

### Overview

Move the sweep's single `git fetch --prune` from after the per-worktree loop to
before it, and run it on a dry run as well as a real one, so both the check
phase and the removal phase decide against the same, current refs.

The dry-run half is the part that needs justifying, because ADR-0006 puts
`--dry-run` on every mutating script. The carve-out is narrow and is the
reason for it: `git fetch --prune` writes only remote-tracking refs under
`refs/remotes/`, mirroring what the remote already says. It creates, moves and
deletes nothing under `refs/heads/`, nothing in any worktree, nothing in the
tracker - the three things `/wurk:cleanup`'s dry run exists to promise it will
not touch. Against that, `/wurk:cleanup`'s flow makes a dry run that skips the
fetch actively harmful: its check phase (`skills/wurk:cleanup/SKILL.md:80-90`)
is what selects candidates, and the real removal (step 3) is only ever invoked
by name for a candidate the check phase already named. A dry run deciding
against stale refs would refuse the rebase case, never name it a candidate, and
the removal that would have succeeded never runs - the bug this bead is fixing,
reintroduced one level up.

Alternatives rejected: fetching lazily on the first diverged worktree (same
dry-run question, plus per-sweep state); and `git fetch --dry-run`, which
updates nothing and so answers nothing.

**The carve-out has to be written down where a kit author reads it, not only
in an ADR.** `skills/wurk:kit/REFERENCE.md`'s `--dry-run` section says
"executes nothing", unqualified, and its kit-author checklist restates it as
"only actually invoke `Sh.run` when `options[:dry_run]` is false". After this
phase `worktree_cleanup.rb` is the one script that does not match that
sentence, so REFERENCE.md is edited in this same commit. Otherwise the
operative document keeps telling every future author something the code no
longer does, discoverable only by someone who happens to read ADR-0017 and
separately notice REFERENCE.md was never touched.

Ordering: after `enumerate` and after the `worktrees.empty?` early return, so a
failed survey and an empty sweep still shell out to nothing new.

### Changes Required:

#### 1. The sweep entry point
**File**: `skills/wurk:kit/scripts/worktree_cleanup.rb`
**Changes**: move the fetch block from `:77-84` to just before
`worktrees.each`, run it unconditionally, and rewrite the comment to say why

```ruby

# not an exception to ADR-0006's dry-run rule - a fetch writes only
# remote-tracking refs, and touches no branch, no worktree, and no

Sh.run(%w[git fetch --prune], envelope: env)
```

#### 2. The dry-run contract, where kit authors read it

## Phase 2: Patch-equivalence decides the sha inequality

### Overview

Add the probe and wire it in, in one commit: a helper with no caller is not
independently gate-verifiable, and the two acceptance-criteria tests exercise
the script end to end anyway.

The equality path is untouched and stays first, so the common case costs no
extra git call and the behavior of every already-passing test that matches
shas is unchanged.

### Changes Required:

#### 1. The probe
**File**: `skills/wurk:kit/scripts/worktree_cleanup.rb`
**Changes**: a public module method (public so a test can drive its output
parsing directly, the same way `WorktreeSurvey.parse_porcelain` is), returning
one of three states.

```ruby
# Whether every commit this worktree carries already has a
# patch-equivalent on `upstream`. Three states, because "could not
# tell" must not read as "nothing left": :equivalent (safe to remove),
# :diverged (a commit is not upstream under any sha), :unknown (the
# probe itself failed).
#
# This is NOT the ancestry check request_state.rb's header bans, in
# two respects. Direction: the forge has already said this request
# merged, and git is consulted only to REFUSE - it can never declare a
# merge here, so its failure mode is a kept worktree, not a silent
# no-op. Power: `git cherry` matches on patch id, so it answers
# correctly in exactly the case plain ancestry gets wrong, a rebase
# that replayed the commits under new shas. Plain ancestry is
# subsumed - when a tip is an ancestor, `upstream..HEAD` is empty and
# the output below is empty too.
#
# Same probe /wurk:cleanup's SKILL.md tells an operator to run by
# hand, with the same all-"-" rule; it moved in here because the skip
# it disambiguates reads like unlanded work and mostly never got
# probed.
def patch_equivalence(path, upstream, env)
  result = Sh.run(["git", "cherry", upstream, "HEAD"], chdir: path, envelope: env)
  return [:unknown, err_or(result, "git cherry #{upstream} HEAD failed")] unless result.success?

  unmatched = result.out.to_s.each_line.map(&:strip).select { |line| line.start_with?("+") }
  return [:diverged, "#{unmatched.length} commit(s) not on #{upstream}"] unless unmatched.empty?

  [:equivalent, nil]
end
```

Ruby 2.6 floor: `each_line`, `map`, `select`, `start_with?`, `empty?` only -
no `filter_map`, no `tally`.

#### 2. The wiring
**File**: `skills/wurk:kit/scripts/worktree_cleanup.rb`
**Changes**: `cleanup_one` takes the manifest (threaded from `run`, which
already holds it at `:49`) and consults the probe when, and only when, the
shas disagree. The refusal string is kept verbatim so nothing downstream or in
the dated research documents is renamed; the two new outcomes get their own
strings.

```ruby
rewritten = false
if head_res.success? && local_head != request["head_oid"]
  upstream = manifest.remote_default_branch
  state, detail = patch_equivalence(path, upstream, env)

  if state == :diverged
    return [{ path: path, branch: branch,
              result: "commits after merge (#{local_head} != #{request['head_oid']}), skipped" }, []]
  end

  if state == :unknown
    env.warn(code: "patch_equivalence_unknown",
             message: "could not compare #{path} against #{upstream}: #{detail}")
    return [{ path: path, branch: branch,
              result: "commits after merge (#{local_head} != #{request['head_oid']}), unverified, skipped" }, []]
  end

  rewritten = true
end
```

`rewritten` then decorates the removal strings, so an operator can see that a
removal rested on the probe rather than on a sha match:

- `"merged in request #42, removed"` (unchanged, shas matched)
- `"merged in request #42 (local tip rewritten, patches already on origin/main), removed"`
- the same two shapes with `would remove` under `--dry-run`

`origin/main` there is the interpolated `manifest.remote_default_branch`, never
a literal - `Contract::HARDCODED_REFS` (`test/contract_test.rb:283-287`) fails
the gate on a literal one.

Watch the word "force": `worktree_cleanup_test.rb:204-210` asserts it appears
exactly once in this file, on a comment line. Write "rewritten" or "re-pushed".

#### 3. The tests
**File**: `skills/wurk:kit/scripts/test/worktree_cleanup_test.rb`
**Changes**: the acceptance criteria, both halves, plus the unverifiable case.
Each drives the full script; the removal assertions are negative-by-construction,
since an unregistered argv raises `FakeSh::UnexpectedCommand`.

- `test_a_rewritten_tip_whose_patches_all_landed_is_removed_and_its_beads_gathered`
  - the wu-mya.6 shape: `git rev-parse HEAD` returns the pre-rebase sha

`request_state.rb`'s header, and the distinction that makes it not one -
direction of risk, and patch id versus ancestry - is exactly the kind of thing
CLAUDE.md says to settle once and cite by number rather than re-argue. The
dry-run fetch carve-out belongs in the same record.

Doc-only; the gate has nothing to say about it beyond staying green.

### Changes Required:

#### 1. The ADR
**File**: `docs/adr/0017-patch-equivalence-as-the-post-merge-divergence-signal.md`
**Changes**: new, following the shape of the existing records (Status,
Context, Decision, Consequences). Content:

- Context: the forge-state merge signal and the banned ancestry alternatives
  (citing ADR-0006 and `request_state.rb`'s header); the sha-equality check and
  what it was for; the wu-mya.6 reproduction and the research section it
  settled.
- Decision: the forge's merged state remains the only merge signal; an
  inequality between the local tip and the recorded head is decided by
  patch-id containment against the manifest's remote default branch; anything

- Consequences: the named failure modes (squash of a multi-commit branch,
  conflict-resolved rebase, empty commit, stale or failing probe) all resolve

## Testing Strategy

### Unit Tests:

All in `skills/wurk:kit/scripts/test/worktree_cleanup_test.rb`, driven through
`WorktreeCleanup.run` with `FakeSh` and the `worktree` manifest fixture
(`remote_default_branch` = `origin/main`), except the parsing cases, which call
`WorktreeCleanup.patch_equivalence` directly.

- **The two acceptance cases.** A rewritten tip whose every commit is
  patch-equivalent upstream is removed, its branch deleted, and `zz-abc`
  gathered into `beads_to_close`; a tip carrying an unmatched commit is skipped,
  with no removal, prune, or branch-delete expectation registered so any such
  call raises.
- **Mixed output.** One `-` line and one `+` line refuses - the rule is
  "every line", not "any line".
- **Unverifiable.** A non-zero `git cherry` refuses with the `unverified`
  result and a `patch_equivalence_unknown` warning.
- **No probe on the fast path.** The shas-match test asserts `git cherry` is
  absent from `@fake.calls`.
- **Fetch ordering.** The fetch precedes the first `git rev-parse HEAD` in
  `@fake.calls`; a failed survey fetches nothing; `--dry-run` fetches but
  removes nothing.
- **Parsing.** Empty output, all-`-`, any `+`, non-zero exit.
- **Unchanged invariants.** The existing dirty-worktree, unsupported-forge,
  forge-unavailable, no-`bd close`, and `force`-word tests stay as they are and
  must not need edits beyond the fetch expectation - if one of them needs more,
  the change went wider than this plan.

### Manual Testing Steps:

1. Build the wu-mya.6 shape in a throwaway repo: a branch, a request merged
   after its history was rewritten server-side, the local branch left at the
   pre-rewrite sha, the worktree clean.
2. `ruby skills/wurk:kit/scripts/worktree_cleanup.rb --dry-run` - expect
   "would remove" with the rewritten-tip clause, not "commits after merge".
3. Run it for real by name and confirm the worktree, the branch, and
   `data.beads_to_close` all behave: removed, deleted, and the bead id present.
4. Add one local commit that is not upstream and repeat: expect "commits after
   merge, skipped", and confirm `git worktree list` still shows it.
5. Make the tree dirty and repeat: expect "dirty, skipped", ahead of any probe.
6. With the network off, repeat step 2: expect the fetch warning path and a
   refusal, never a removal.
